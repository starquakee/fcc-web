### 从会回答的模型，到能工作的系统

早期谈 Agent 时，我们常用一个非常顺手的公式：Agent 等于 LLM、记忆、工具、规划和行动。这个公式很适合入门，因为它把聊天模型和能做事的执行体区分开来。模型不再只是生成文字，它还要记住上下文、拆解任务、调用工具、观察结果，并继续下一步。

但这个公式一进入真实工作场景就显得太薄。一个企业里的 Agent 不只要完成一次演示，它要面对长任务、中断恢复、权限边界、工具失败、上下文膨胀、评估缺失、多人协作和线上回滚。真正决定它能不能稳定工作的问题，往往已经不在模型内部，而在模型外层的运行系统里。

这层外壳就是 Harness。它不是一个更花哨的提示词，也不是把几个工具随便接到模型上，而是决定 Agent 如何接收上下文、如何规划、如何调用工具、如何保存状态、如何验证结果、如何接受权限约束，以及如何在失败后继续迭代的工程系统。

可以把模型看作发动机，把 Agent 看作正在执行任务的驾驶员或工作单元，把 Harness 看作车辆、仪表盘、道路规则、维修记录和安全系统。没有 Harness，模型可以回答问题；有了 Harness，模型才更像一个能长时间承担工作的系统。

### 工作流，比单次推理更重要

好的 Harness 首先要定义可执行的工作流，而不是只给模型一段提示词。真实任务通常不是一次回答能结束的，它们更像一组循环：先制定计划，再执行一步，观察工具返回，运行验证，反思失败，修正方案，然后继续推进。

这就是 Loop Engineering 的价值。它把“自我纠错”从一句口号变成运行时机制。Agent 每一步都能看到命令输出、测试结果、错误日志和中间产物，再决定下一步该继续、回退、分支探索，还是请求人类介入。对代码、研究和数据分析这类长任务来说，一个好的循环常常比一次更聪明的推理更重要。

循环还要有停止条件。Agent 什么时候算完成，什么时候应该承认失败，什么时候必须升级给人，这些都不能完全交给模型临场猜测。Harness 需要把这些条件写成系统规则，让“继续努力”和“及时停下”都变成可控动作。

### 上下文不是越多越好

长任务会产生大量轨迹：用户偏好、历史决策、命令输出、实验日志、代码 diff、错误栈、论文摘要和评审意见。如果把所有东西都塞进提示词，成本会爆炸，模型也会被噪声拖垮。

Harness 要做的是上下文工程。它要判断哪些信息进入当前窗口，哪些写进文件，哪些压缩成摘要，哪些变成可检索记忆，哪些只保留在审计日志里。上下文不是一个无限大的袋子，而是一套持续整理和分层取用的信息系统。

我很喜欢把文件系统当作持久记忆的思路。文件、日志和状态记录足够朴素，却非常可靠。它们可以跨回合、跨进程、跨重启保留下来，也能被人类审计。对很多 Agent 项目来说，把关键状态写清楚，比追求复杂的记忆架构更有价值。

### 状态管理，是长任务的骨架

企业场景里的 Agent 往往要跑很久，甚至分多天完成。它不能因为会话中断、服务重启或上下文裁剪就失去方向。Harness 必须保存当前目标、已完成步骤、待办事项、关键中间产物、失败原因和下一步建议。

这类状态记录让任务可以恢复，也让协作变得可能。人类可以接手，另一个 Agent 可以接手，原来的 Agent 也可以在压缩上下文后继续工作。没有状态管理，所谓长期 Agent 其实只是在一次又一次重新猜测自己之前做过什么。

状态还承担另一种职责：防止实现漂移。任务越长，Agent 越容易从原方案滑向更常见但不正确的简化实现。如果 Harness 持续保存目标、约束和关键决策，系统就更容易发现自己是不是偏离了原来的问题。

### 工具越强，权限越要清楚

Agent 的价值来自它能操作外部世界。它可以读文件、查数据库、改代码、发消息、提交工单，甚至触发付款或删除资源。也正因为如此，工具系统和权限控制必须成为 Harness 的一等公民。

好的 Harness 会区分只读工具、低风险写操作和高风险操作。敏感动作需要审批、审计或沙箱；数据访问要遵循最小权限；工具调用参数要可校验；失败结果要完整反馈给 Agent，而不是静默吞掉。

这里的关键不是让 Agent 什么都不能做，而是让行动拥有边界。一个没有工具的 Agent 很难产生真实价值，一个没有权限系统的 Agent 又很难被放心使用。Harness 要做的，是让能力和约束一起生长。

### 没有评估，就没有改进

Harness 还必须内置评估。对代码 Agent 来说，评估可能是类型检查、单元测试、集成测试、lint 和回归用例；对研究 Agent 来说，可能是证据链检查、实验复现、引用核验和结果审计；对业务 Agent 来说，可能是任务成功率、人工接管率、风险事件率和用户满意度。

评估不应该只出现在上线后的报表里。它应该进入运行主循环。Agent 做完一步后，Harness 自动跑验证，把失败模式反馈给 Agent，Agent 再基于反馈继续修正。这样失败不是终点，而是下一轮行动的输入。

更成熟的系统还要小心奖励黑客。Agent 会优化你给它的信号。如果只看单元测试，它可能过拟合测试；如果只看评审模型，它可能学会讨好评审；如果评估器太弱，自我改进就会变得危险。因此 Harness 不只要有评估，还要有留出任务、回归检查和人工裁决点。

### 并行需要可观察

复杂任务常常需要并行探索。一个 Agent 可以让子任务分别验证不同假设、检索不同资料、修改不同模块，或让后台任务持续跑实验。但并行如果只是一堆临时对话，很快就会失控。

Harness 需要像小型进程管理器一样工作。它要能启动任务、检查日志、取消失败任务、汇总结论，并把关键结果合并回主线程。子 Agent 的价值不在于数量，而在于每条支线都有可观察的状态、可追溯的日志和明确的合并规则。

这也是为什么轨迹很重要。成功轨迹告诉我们什么有效，失败轨迹告诉我们系统短板在哪里。好的 Harness 会保存失败尝试，因为它们能防止 Agent 反复走同一条错路，也能把一次失败沉淀成下一版工作流的改进。

### Self-Harness，不是让系统失控地改自己

Lilian Weng 那篇文章最有启发的一点，是把 Harness 本身也视为优化对象。优化路径可以从提示词开始，逐步走向结构化上下文、工作流、Harness 代码，甚至优化器代码。越往后，优化对象越接近“产生好答案的机制”，而不只是某一次答案。

一个典型的 Self-Harness 循环大致包括三步。先收集执行轨迹和评估结果，把失败聚类成可解释的模式；再让 Agent 基于失败模式、可编辑范围、成功案例和历史尝试提出 Harness 修改；最后用回归测试和留出任务验证候选，只有没有引入退化的改动才进入新版本。

这并不意味着让 Agent 无限制地修改自己。恰恰相反，越是自我改进，越需要把可编辑面、评估器、权限控制和人工审核放在更外层。否则系统可能学会迎合评估器、绕过约束，或者把短期指标优化到长期质量受损。

### 好 Harness 的判断方式

判断一个 Harness 好不好，可以先问几个问题。任务中断、工具失败或上下文裁剪后，Agent 能否恢复？系统是否知道自己做得好不好，是否有自动化验证和回归检查？敏感操作是否有权限边界、审批和审计？人能否从轨迹、日志和状态里看出 Agent 为什么这么做？

还要问更长期的问题。失败模式能不能沉淀为工作流或上下文机制的改进？优化目标有没有覆盖维护成本、兼容性、数据安全和长期质量，而不只是短期成功率？人类是不是被放在目标澄清、风险动作、质量裁决和方向选择这些更高价值的位置上？

如果这些问题都有清楚答案，Agent 才更像一个工程系统，而不是一个表现偶尔惊艳的演示。

### 结语

Agent 的核心不只是“模型会不会想”，还包括系统如何让它想、如何让它行动、如何让它记住、如何让它被验证、如何让它被约束。Harness 就是这层工程化外壳。

早期 Agent 框架解决的是“让模型能用工具”。Harness Engineering 解决的是“让模型在真实环境里长期、可靠、可控、可改进地工作”。未来更强的模型会吸收一部分手工 Harness 技巧，但外部工具、状态、权限、评估和人类监督不会消失。它们会成为 Agent 系统真正的工程底座。
