### 从一句公式说起

早期讲 Agent，大家很喜欢用那个公式：Agent 等于 LLM 加记忆、工具、规划和行动。它确实好用，至少能把聊天模型和会做事的执行体分开。模型不只是说话了，它要看任务、拆步骤、调工具、读结果，再决定下一步。

可这个公式一落到真实工作里，就有点薄了。一个 Agent 如果只跑 demo，当然可以靠 prompt 撑一阵。可一旦任务变长，中间会断，会失败，会遇到权限边界，会产生一堆日志和中间文件。问题就变了：不是模型能不能回答，而是整个系统能不能让它继续干活。

我现在更愿意把 Harness 理解成 Agent 外面的那套运行环境。它管上下文怎么给，工具怎么调，状态怎么存，结果怎么验，风险动作怎么拦，失败后怎么接着走。

如果硬要打个比方，模型像发动机，Agent 像正在开车的人。Harness 是车身、仪表盘、路规、维修记录和刹车系统。只有发动机也能响，但你不会把它直接扔上高速。

### Loop 不是一句自我纠错

很多 Agent 系统喜欢在提示词里写“请反思并修正”。听起来很聪明，实际效果经常看运气。真正有用的是把循环写进运行时。

一个最基本的循环大概是：计划一步，执行，观察结果，验证，改方案，再执行。代码任务里是跑测试和看报错。研究任务里是查证据和补引用。数据任务里是看中间结果有没有跑偏。Agent 不是一次想明白，而是在工具反馈里慢慢把问题磨出来。

这里最容易被忽略的是停止条件。什么时候算完成？什么时候该承认这条路走不通？什么时候必须问人？这些都不能全靠模型临场判断。Harness 要把这些规则放在外面，像护栏一样立着。

### 上下文要收拾

长任务会制造垃圾，也会制造宝贝。命令输出、错误栈、用户偏好、历史决定、实验记录、代码 diff、论文摘要，全都可能有用，但不可能全塞进提示词。

所以我觉得上下文工程的核心不是“给更多”，而是“会收拾”。当前窗口里只放当下需要的东西。重要结论写进文件。长日志压成摘要。以后可能复用的经验放进可检索记忆。纯审计信息就留在轨迹里，不要每轮都端上桌。

文件系统在这里意外地好用。它不花哨，但可靠。一个目标文件、一个进度记录、几段失败原因，往往比复杂记忆模块更能救场。服务重启也好，上下文压缩也好，文件还在那里。

### 状态比记性可靠

很多所谓长期 Agent，其实只是每次重新猜自己之前做过什么。真正的长期任务需要状态。

状态里应该有当前目标、已完成步骤、待办、关键中间产物、失败原因和下一步建议。这样会话断了还能接，人类也能半路介入。另一个 Agent 接手时，不需要从一堆聊天记录里考古。

状态还有一个更细的用处：防止实现漂移。任务一长，Agent 很容易从原方案滑到一个更常见、更顺手、但不对的实现。目标、约束和关键决定如果一直写在状态里，偏航就更容易被发现。

### 工具权限别靠自觉

Agent 真正有价值，是因为它能动外部世界。读文件、查数据库、改代码、发消息、提交工单，这些都不是纯文本游戏。

也正因为能动，权限就不能只靠一句“请谨慎”。只读工具、低风险写操作、高风险操作，最好分清楚。删除资源、外发消息、付款、改权限，这些动作要有审批或沙箱。工具失败也要原样反馈给 Agent，别静默吞掉。

这不是把 Agent 绑住。相反，边界清楚之后，它才敢做更多事。没有工具，Agent 很难产生现实价值。没有权限系统，大家又不敢让它碰真东西。

### 评估要进循环

没有评估，Agent 的自我改进很容易变成自我感觉良好。

代码 Agent 可以跑类型检查、单元测试和回归用例。研究 Agent 要查引用和证据链。业务 Agent 至少要看任务成功率、人工接管率和风险事件。不同场景不一样，但共同点是：评价不能只在最后写进报表，它要进入主循环。

Agent 做完一步，Harness 立刻跑验证。失败就把失败模式扔回去，让下一步修正。这样失败不是终点，而是下一轮输入。

也要小心奖励黑客。只看测试，Agent 可能过拟合测试。只看评审模型，它可能学会讨好评审。评估器越弱，越不能放开让系统自我改进。留出任务、回归检查和人工裁决点，都得留着。

### 并行不是开几条聊天

复杂任务确实适合并行。可以让不同子任务查不同方向，验证不同假设，或者改不同模块。但并行如果只是开几条临时聊天，很快就乱。

Harness 要像一个小型任务管理器。它能启动任务，读日志，取消失败分支，汇总结论，再把有用结果合回主线。子 Agent 的价值不在数量，而在每条支线有没有状态、日志和合并规则。

失败轨迹也要留。成功告诉你哪里有效，失败告诉你系统会怎么摔。好的 Harness 不怕保存失败，因为失败记录能防止同一条错路反复出现。

### Self-Harness 需要更硬的边界

Lilian Weng 那篇文章里，我最在意的一点是：Harness 本身也可以被优化。先改提示词，再改上下文结构，再改工作流，最后甚至改 Harness 代码。越往后，改的就越接近“产生好结果的机制”。

但这件事不能浪漫化。让系统改自己，听起来很酷，实际很危险。可编辑范围要小，评估器要在更外层，权限要硬，人工审核不能省。

一个比较稳的 Self-Harness 循环应该是这样：先收集轨迹和评估结果，找出失败模式。再让 Agent 提一个边界很清楚的改动。最后用回归任务和留出任务验证。没退化，再合进去。

如果跳过这些外层约束，系统很可能学会钻评估器空子。短期分数好看，长期质量变差。

### 我会怎么判断一个 Harness

我会先问几个很土的问题。任务断了能不能恢复？工具失败有没有留下可读信息？上下文被压缩后，Agent 还知道自己在干什么吗？敏感动作有没有审批？人能不能从日志里看出它为什么这么做？

然后再问长期一点的问题。失败会不会变成下一版工作流的改进？评估有没有覆盖维护成本和安全风险？人是不是被放在真正需要判断的位置上，而不是被迫盯每一步操作？

这些问题如果答不上来，再聪明的模型也只是一个容易失忆、容易冲动的执行器。

### 收尾

Agent 的问题不只在模型会不会想。更现实的问题是：系统怎么让它想，怎么让它行动，怎么让它记住，怎么验证它，怎么在它越界前把它拉住。

早期 Agent 框架解决的是“模型怎么用工具”。Harness Engineering 关心的是“模型怎么在真实环境里长期工作”。以后模型会变强，很多手工技巧会被吸收掉。但工具、状态、权限、评估和人类监督不会消失。

它们可能才是 Agent 真正的工程底座。
