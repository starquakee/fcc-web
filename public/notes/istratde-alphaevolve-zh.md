### 那个让我卡住的相似感

最近把 AlphaEvolve 和 iStratDE 放在一起看，越看越觉得它们有点像。不是表面像。一个是 LLM 写代码，一个是 Differential Evolution 做连续优化，乍看根本不是一类东西。

可如果把对象拿掉，只看搜索方式，它们都在做一件事：不要太早押注单一路径。保留一批行为不一样的候选，让它们在评价信号里竞争。好的留下来，差的慢慢被挤掉。

AlphaEvolve 的多样性在 program database 里。不同程序、不同修改路线、不同分数会被保存下来，后面再被采样成 parent 或 inspiration。iStratDE 的多样性在个体身上。每个个体一开始就拿到不同的 mutation、crossover 和参数组合，之后一直按自己的风格搜索。

一个是 archive-level diversity，一个是 individual-level diversity。听起来是两个词，背后其实是一件事：别让整个系统只有一种脑回路。

### MAP-Elites 这条线很重要

MAP-Elites 最吸引我的地方，不是它又提出了一个优化算法，而是它换了目标。传统优化总想找一个最优解。MAP-Elites 更像是在画地图：不同格子里放不同类型的好解。

AlphaEvolve 明确说过，它的 evolutionary database 受 MAP-Elites 和 island model 启发。它不把所有历史压成一个冠军程序，而是保留一片候选生态。有些程序结构怪一点，有些在某个指标上好一点，有些可能暂时不是最强，但能给下一轮生成带来新方向。

iStratDE 也有类似味道。它没有显式的行为网格，也没有 archive，但它让 population 变得不一样了。个体不只是坐标不同，它们的搜索方式也不同。这个变化很微妙，却很要命。

所以我现在更愿意把 iStratDE 看成一种设计原则：如果中心化 adaptation 又贵又容易出问题，就把策略差异直接放进个体里。让一群搜索者天生不同，再让评价函数说话。

### iStratDE 还可以再往里挖

iStratDE 论文里最显眼的优点是简单。初始化时分策略，之后不更新。没有复杂 archive，没有 success-history，没有全局协调。也因为这样，它非常适合 GPU。

但我觉得更有意思的地方在另一个层面：它把“策略”变成了个体的一部分。

传统 DE 里，个体通常只是一个候选解。策略在算法外面，是全局配置。iStratDE 把两者绑到一起后，population 就不只是一堆点了。它变成一堆带着不同搜索习惯的点。

这里至少有几个方向还能挖。

第一个是给策略画像。现在我们知道 PoolSize 变小会伤性能，但还不知道每类策略具体在干什么。有的可能更会探路，有的更会收敛。有的步子大，有的步子稳。能不能把这些行为测出来，给策略做一张地图？如果能做到，随机策略池就不只是随机了。

第二个是让策略轻微遗传。iStratDE 不做 adaptation，这很干净。但也可以试一种更弱的版本：强个体不只传坐标，也传自己的策略。策略可以小幅变异，可以跟随个体一起被选择。这样不会变回那种中心化调参系统，却能让策略本身参与进化。

第三个是接 archive。iStratDE 的多样性主要活在当前 population 里，AlphaEvolve 的多样性主要存在历史 database 里。两者接起来很自然：当前 population 负责高吞吐探索，archive 保存不同风格下的好结果，再反过来影响下一轮初始化或采样。

这件事一旦接上，就有点像 MAP-Elites 了，只是格子未必是人为定义的行为描述符，也可能是自动归纳出来的搜索风格。

### 为什么我会想到 LLM Agent

LLM Agent 本来就不是一个模型裸跑。真正影响结果的东西很多：prompt 怎么写，工具怎么用，上下文怎么取，失败后怎么反思，temperature 设多少，先写测试还是先改代码，愿不愿意查资料，敢不敢大改。

现在我们经常把这些揉进一个系统提示词里，试图做出一个“全能 Agent”。它要会谨慎，也要会冒险。要会检索，也要会直接动手。要会小步修，也要能大重构。听起来很全，其实很拧巴。

iStratDE 给了一个反方向：别让一个 Agent 学会所有性格。直接放一组风格固定的 Agent。

比如一个 Agent 永远 test-first，一个偏快速原型，一个像代码审稿人，一个只做最小修改，一个喜欢查资料，一个专盯性能。它们拿到同一个任务后并行试，最后由测试、benchmark、引用核验或人来筛。

关键不是“多叫几个 Agent 来聊聊”。关键是每个 Agent 的策略身份要稳定。稳定之后才有观察价值。你会慢慢知道，哪种任务适合哪类风格。失败也会变得可解释一点。

### iStratAgent 可以很朴素

如果要做一个原型，我会先叫它 iStratAgent。

第一步，定义策略池。这里的策略不是 DE 里的 mutation/crossover，而是一组 Agent 行为：prompt 风格、工具调用节奏、上下文选择、生成温度、验证偏好、改动幅度、是否主动造反例，甚至对速度和可维护性的偏好。

第二步，初始化一批 Agent。每个 Agent 固定拿一个策略组合，在一段任务周期里不变。它们可以并行解同一个问题，也可以分头处理子问题。

第三步，评价候选。代码任务就跑测试和静态检查。算法任务就跑 benchmark。RAG 任务要查引用和答案。主观任务也能做，但我不建议一开始就碰，评估器太容易被哄。

第四步，维护 archive。archive 不能只存最后的答案。它还应该存路线：哪种 prompt 模板有效，哪种诊断顺序有效，哪个测试构造抓住了问题，哪个失败恢复策略值得复用。

这样一来，底层是 iStratDE 式的固定异质个体，上层是 AlphaEvolve 式的历史数据库。一个负责并行试，一个负责记住什么试法有用。

### 先拿什么做实验

我会从可验证任务开始。代码修复最合适：给 failing tests，让不同策略 Agent 各自修，再比较通过率、diff 大小、修改风险和耗时。

算法发现也适合。给一个 skeleton 和 evaluator，让 Agent 修改 evolve block。这个方向和 AlphaEvolve 更贴近，也能比较清楚地看到 archive 有没有帮助。

RAG 可以做，但要小心。最好选那种有标准答案、引用可查的集合。不然很容易变成一堆答案看起来都挺像那么回事，最后谁也说不清哪个真的好。

对照组也不用复杂。单 Agent，同质多 Agent，随机多 Agent，iStratAgent，iStratAgent 加 archive。看固定预算下谁更稳，谁更会恢复，谁在新任务上不容易崩。

如果这些实验能跑通，后面的问题就更有意思了。哪些策略互补？哪些只是噪声？任务类型能不能映射到策略分布？archive 里的旧轨迹能不能帮新任务冷启动？这比继续手调一个万能 prompt 更像研究。

### 我现在的判断

iStratDE 的潜力不只在 DE。它提醒我一件事：智能系统未必都要靠一个越来越聪明的中心控制器。只要评价信号还算可靠，并行预算足够，很多能力可以来自结构化多样性。

AlphaEvolve 从另一个方向给了例子。它用 LLM 生成候选，用 evaluator 把候选拉回现实，用 database 保存多样的高分程序。它不是一次 prompt 写得好，而是整套 harness 在工作。

所以我会把它们放在同一个问题下：怎么把多样性变成算力？

iStratDE 给的是个体级策略多样性。AlphaEvolve 给的是程序级 archive 多样性。未来的 LLM Agent 系统大概两者都需要：一边让不同风格的 Agent 并行探索，一边让 archive 记住哪些风格、哪些轨迹、哪些结构真的有用。

多样性本身当然不神奇。没有评价，它只是噪声。没有记忆，它很快消失。没有结构，它只会把系统搞乱。

但一旦评价、记忆和结构都在，多样性就不只是“多试几个”。它会变成一种可以调度的搜索资源。
